# Системная инженерия для StatusProject

## Цель
Применять системную инженерию к `StatusProject` как к легкой системе управления состоянием долгой работы, а не как к набору разрозненных Markdown-файлов.

## Граница системы
`StatusProject` отвечает за сохранение контекста, правил, решений, задач и точки продолжения между сессиями человека и ИИ-агента.

Внутри границы:
- инструкции для агента;
- шаблоны state-файлов;
- текущие state-файлы проекта;
- правила обновлений, публикации и релизов;
- карта ссылок и инструментов.

Вне границы:
- бизнес-логика целевого проекта;
- приватные локальные данные целевого проекта;
- секреты, токены, чувствительные логи;
- ручное управление UI, если задачу можно решить через файлы и команды.

## Заинтересованные стороны
| Сторона | Что ей нужно от системы |
| --- | --- |
| Владелец проекта | Предсказуемое продолжение работы без потери контекста |
| ИИ-агент | Короткий вход, понятные правила, актуальные state-файлы |
| Целевой репозиторий | Минимальный набор файлов без лишней бюрократии |
| Релизный процесс | Понятные версии, changelog и безопасная публикация |

## Требования
- Минимальное включение системы: `TODO`, `MEMORY`, `PROJECT-RESUME`.
- Сложные работы должны иметь явную стратегию в `PLAN`.
- Архитектурные сведения должны жить в `ARCHITECTURE`.
- Инфраструктурные среды должны быть названы явно: `prod`, `staging`, `dev`, `local`.
- Обновления шаблонов нельзя проверять чаще одного раза в 7 дней на проект.
- Локальное состояние целевого проекта нельзя перезаписывать без согласия пользователя.

## Компоненты
- `AGENTS.md` / `CLAUDE.md`: короткие совместимые входы.
- `PROMPT*.md`: канонический режим работы.
- `START-HERE*.md`: быстрый старт.
- `templates/`: переиспользуемые англоязычные шаблоны.
- `TODO` / `MEMORY` / `PROJECT-RESUME`: минимальная оперативная память проекта.
- `PLAN` / `STATUS-LOG` / `STATE-HISTORY`: управление длинными потоками.
- `ARCHITECTURE` / `INFRASTRUCTURE` / `SOFTWARE` / `MCP`: доменные карты.
- `CHANGELOG.md` / `VERSIONING.md`: релизы и история изменений.

## Контракты
- Входные инструкции должны быть короткими и ссылаться на канонические документы.
- Шаблоны должны оставаться компактными и англоязычными.
- State-файлы должны быть пригодны для старта следующей сессии без чтения всего чата.
- Любое изменение процесса должно отражаться в соответствующих русской и английской версиях, если оно меняет поведение агента.
- Публичные релизы должны быть согласованы с `CHANGELOG.md`, тегами и `VERSIONING.md`.

## Риски
| Риск | Последствие | Контроль |
| --- | --- | --- |
| Разрастание инструкций | Агент теряет главный путь | Держать root-входы короткими, детали в канонических файлах |
| Несогласованность RU/EN документов | Разные агенты следуют разным правилам | Обновлять парные документы вместе |
| Перезапись локального state | Потеря пользовательского контекста | Требовать согласие перед заменой state-файлов |
| Шаблонная бюрократия | Пользователь не применяет систему | Минимум файлов для включения, доменные файлы только по необходимости |
| Слабая релизная дисциплина | Непонятно, что изменилось | Changelog, versioning checklist, теги |

## Проверка
Перед релизом или крупным изменением проверять:
- понятна ли граница системы;
- не сломан ли минимальный набор `TODO` / `MEMORY` / `PROJECT-RESUME`;
- обновлены ли связанные RU/EN документы;
- отражены ли новые файлы в README, LINKS или changelog, если они стали частью публичного интерфейса;
- не добавлены ли секреты или локальные state-файлы в публикацию;
- есть ли понятный следующий шаг в `PROJECT-RESUME`.
